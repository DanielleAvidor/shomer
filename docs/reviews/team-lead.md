# Team-lead review: Shomer as a CV artifact (student PM)

Reviewed: README, PRD, HANDOFF, research notes, eval, engine/tests (135 pass locally, 0.7s), Kotlin app, both workflows, docs/index.html, git log. 5-minute read, not an audit.

## What is genuinely good (short)
- Honest framing is unusually strong: "never say safe", "links do not vouch for themselves", explicit "Not proven" section, the eval described as tautological, simulated users labelled as not research.
- Real product thinking: the grandmother interview changed the design (she declined family alerts), PRD has a kill/pivot criterion, a cut list, and arithmetic on why 0/25 misses is not 95%.
- Directory with provenance and a verified flag is a real product decision, not a gimmick. Kotlin/Python parity harness is rare and credible.

## REJECTS

1. BLOCKER. Authorship. 22 of 43 commits are "Claude <noreply@anthropic.com>"; the candidate's author line is `noreply@example.com`. The newest, most impressive work (agent, Android, CI, demo) is 100% Claude-authored in git. HANDOFF.md itself lists "fix the commit email" as open. In 10 seconds a reviewer concludes: the candidate did not build this. Demand: fix the author email (GitHub noreply), and add a short "Who decided what" table with commit/PR links to the candidate's own decisions (interview notes, principles, the rejected account-login agent). Do not rewrite history to hide Claude; mark it plainly.

2. BLOCKER. Claims contradict each other about the single most important fact (does the Android app work?). README line 9 and line 24: "has not been compiled or run yet". README lines 41 and 87: "compiles and its unit tests pass in CI". Bottom of README: "never compiled or run". PRD section 12: "Source written, not compiled or run". HANDOFF: compiled in CI. Demand: one status line, repeated nowhere else in conflicting form. Today it should read: "builds and passes unit tests in CI; emulator run: see docs/proof (or: failing, see issue)".

3. BLOCKER. Emulator evidence is promised but does not exist. `docs/proof/` is absent. The e2e workflow was needed to fix two Android crashes (UNICODE_CHARACTER_CLASS, unescaped `]`/`}` in regex) in the last hour, i.e. the app crashed on its first real run, and I have no green run. Nothing in the README links to a run. Demand: do not mention emulator evidence anywhere until docs/proof has screenshots plus RUN.txt from a green run; then link the run URL and commit SHA. Also state that an emulator with synthetic SMS is not a phone with real WhatsApp notifications.

4. MAJOR. README first impression (60 seconds) is bad. 141 lines, English, status caveats in 6 places, no screenshot, no live demo link, no one-sentence result. `docs/index.html` (static demo) exists but README never links it and it carries `noindex`. Sections are appended in chronological order ("Building the Android app (first time)" and "Checking a link on its own" are tacked on below "Next steps"). Demand: top of README = one sentence, one screenshot/GIF, link to the Pages demo, 3 bullets (what is proven, what is not, what I decided). Move build instructions, survey, advisor and agent detail to docs/. Pick a language: Hebrew product, English README is fine, but then HANDOFF (Hebrew, addressed to a chat) must go.

5. MAJOR. HANDOFF.md should not be in a public repo. It is a "paste this into another Claude chat" prompt, says "built as part of Danielle's CV for PM roles", and contains the candidate's full name. It signals the repo is a prompt-handoff artifact. Also `.claude/agents/team-lead-reviewer.md` etc. committed: the "hiring-manager reviewer" is an AI persona that reviews the repo that is shown to hiring managers. Demand: delete HANDOFF.md; move `.claude/` out or into docs/process/ with one paragraph on how it was used; do not call it "review" in the README without "by AI" in the same sentence.

6. MAJOR. Stale and inconsistent numbers across docs. PRD section 12: verified = "Israel Post, Carmel Tunnels, police fines" (now 11 of 16). PRD eval: "0 out of 25 scams" vs eval/results.md 28. PRD status "v0.2" yet includes shipped features. review-round2 reports 9% false alarms and 19% hard misses on legit/scam sets; eval/results.md reports 0/12 false alarms. The gap is because the corpus was extended after the fixes, which is exactly the tautology the README admits, but the headline number a skimmer sees is "0 false alarms, 0 wrongly matched". Demand: one table in README: round-2 adversarial (before fixes) vs corpus (after fixes), with n and confidence intervals, and a line "held-out set: none yet". Regenerate PRD section 12 from directory.json/eval, or delete the counts.

7. MAJOR. Directory "verified" claims are not independently checkable. Sources are prose ("Walla 15.7.2025", "IEC statements quoted by Israel National News"), no URLs, no retrieval dates on all, and the README says "checked 2026-11-21" for 8 organizations added in a single commit (bce3299) that also did code changes. Verification of Israeli bank domains against "their own site" is the one thing the product's trust rests on. Demand: each entry gets `source_url`, `checked_on`, `checked_by`, and the evidence (a quote or screenshot path). Recheck IEC (verified via press, not the company) or mark it unverified. Also reconcile: Hapoalim `poalim.co.il` handling and `unconfirmed_domains` should be explained in one place.

8. MAJOR. User research is thin and partly compromised, and the PRD reads as if it were not. Three people, one family, interviewer is the granddaughter, questions "prepared by Claude", answer options offered (leading), paraphrased not recorded. The repo says this in `docs/research/`, good, but README/HANDOFF call it "three interviews" and "ran the research". The grandmother said family alerts are "not needed"; the product's headline still sells the family loop and the Family tab. Demand: either reposition (independence-first, family opt-in as hypothesis) or show evidence for the family loop. Run at least 5 interviews with non-family older adults before claiming a beachhead; the survey exists but has 0 responses and its README mentions `WA_NUMBER` placeholder.

9. MAJOR. Statistics in PRD are unsourced (2,639 cases / +27%, "hundreds of percent" rise). The PRD admits it, which is honest but a PM artifact whose problem-size slide has no links is weak. Demand: primary-source links (Israel Police, Bank of Israel, INCD) or delete the numbers. Add one real incident from the family (PRD says "to add").

10. MINOR. Repo hygiene. `.gitignore` is fine, but the working tree contains `__pycache__`, `.pytest_cache` (untracked, OK). `.claude/` committed. `docs/review-round2-adversarial.md` sits next to the PRD with "No project files were changed" and "/tmp/t/run.py" (script not in repo, not reproducible). Demand: move reviews to docs/reviews/, commit the script or drop the numbers. CI badge missing; no Python CI workflow at all (only Android). Add one `pytest + eval + parity` workflow and a badge; "135 tests pass" is currently only verifiable by cloning.

11. MINOR. The evaluation script prints "Scams not reported as matches official: 28/28". That is a metric designed to look like 100% while not being a catch rate (results.md says so in parentheses). Detection is 20/28 hard blocks on self-written data. Lead with 20/28 and "7 of 12 legit messages get 'can't verify'" (58% friction). That friction number, not the zero false alarms, is the real product problem for an elderly user, and the PRD target (<=2% false alarms) says nothing about it. Demand: add a friction target and discuss it.

12. MINOR. Competitive section is "desk research, not hands-on" and the differentiation bet (verified official route) is not tested against the obvious competitor the grandmother already uses: asking a chatbot. Demand: run the same 20 messages through a general chatbot and Google Messages and show the table, even with n=20.

13. MINOR. Scope smell. Python engine, Kotlin engine, notification listener, advisor extension point, survey with Apps Script, brand kit, SVG illustration, Claude design canvas link (external, not reproducible, claude.ai artifact URL in a CV repo). For a PM role this reads as engineering sprawl produced by a code generator. The cut list is good; apply it to the repo itself: remove advisor.py ("no real advisor included"), GuardianClient (not built backend), and the artifact link.

## Where the candidate is exposed in the interview (questions I would ask)
- "Walk me through commit 7d87b79 (notification-listener agent). Which parts did you write? Explain the alert policy thresholds without looking." If she cannot explain `agent.py`, the project is a liability.
- "The app crashed on the emulator twice today on regex flags. What does that tell you about the claim 'statically reviewed'?"
- "Your grandmother said family alerts are 'not needed'. Why is the Family tab in v1?"
- "Seven of twelve legitimate messages get 'can't verify'. How many such warnings before she ignores Shomer? What is your metric and your threshold?"
- "A sideloaded debug APK, SMS-receive permission, notification access, restricted settings. How does your grandmother install this? Who is the buyer, how does it ship, why will Google Play allow it?"
- "Your engine only knows 16 organizations. What happens on the 17th? Who maintains the directory and who is liable for a wrong 'matches official'?"
- "Which three decisions did you change after real user input, and which after AI-persona input?"
- "What would you cut if you had two weeks?" (She has a cut list; test whether it is a real prioritization or a README section.)

## Verdict as a CV artifact
Conditional hire-for-interview, not yet a strong portfolio piece: **5.5 / 10** today; **7.5** achievable in a weekend if rejects 1 to 5 are fixed.
Strengths: honesty culture, problem framing, explicit limits, a verifiable test suite. Weaknesses: the commit history says "Claude built it", the status story is self-contradictory, the evidence for Android and for users is not in the repo, and the README does not sell in 60 seconds. A reader who skims sees an AI-generated repo with a human disclaimer; a reader who digs sees good judgment buried. Make the judgment the headline.
Hire/no-hire for this artifact alone: interview yes (the honesty is rare), but only if she can defend agent.py and the research design live; without that, no-hire.
